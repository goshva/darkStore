## 1. Известные проблемы (по результатам тестирования)

### 1.1. Ошибки расчётов
- [ ] **Деление на ноль** в `lineChart`, если все значения `null` или `max === min` — сейчас защита частичная (`|| 1`), нужно покрыть тестами.
- [ ] **Отрицательная прибыль** не подсвечивается отдельным статусом в легенде (сейчас просто балл падает).
- [ ] **`fieldValueNorm`** для строковых полей («да/нет/частично») не учитывает «другое» с текстом — теряется вклад.
- [ ] **`calcQualityScore`** не учитывает, что часть полей недели 2–6 перекрывает неделю 1 (двойной вес).
- [ ] **`buildReasons`** при `prev = null` не показывает дельту, но и не помечает «базовая неделя» — визуально непонятно.
- [ ] **Куратор**: если одно из трёх значений пустое, `Math.min` даёт 0 → штраф применяется некорректно.
- [ ] **`marginPct`** на неделях 2–6 берётся из недели 1, но если пользователь меняет `cost` на неделе 3, маржа не пересчитывается от новой стоимости — нужно явно решить: маржа в % от `courierCost` недели 1 или от текущей `cost`.

### 1.2. Ошибки отчёта для ИИ
- [ ] **Нет версии модели** в отчёте — ИИ не понимает, к какой версии формул относится вывод.
- [ ] **Нет единиц и допущений** по каждому весу потерь — ИИ может неверно интерпретировать \(k_L = 0.5\).
- [ ] **Нет baseline**: не указано, что считать «до перезагрузки» (неделя 1 или внешний бенчмарк).
- [ ] **Нет ограничений реальности**: ИИ может предложить стратегию, невозможную при текущих слотах/кураторах.
- [ ] **Нет формата ответа**: ИИ возвращает свободный текст, а нужен JSON со стратегией, чтобы сравнивать прогоны.
- [ ] **Нет дедупликации причин**: «опоздания» и «обращения» часто связаны, ИИ может дать противоречивые решения.

### 1.3. Ошибки UI/поведения
- [ ] **YouTube-полоса** при быстром вводе «дёргается» — нужна `requestAnimationFrame`-батчинг.
- [ ] **Легенда** обновляется на каждое нажатие клавиши — при вводе текста это лишние перерисовки.
- [ ] **`flash`-подсветка** срабатывает и на ползунках, не влияющих на маржу (например, `avgKm`) — нужно ограничить список.
- [ ] **`localStorage`** без версии ключа: при смене схемы старые данные ломают рендер. Нужна миграция.
- [ ] **`resultEl` и `aiReportEl`** перезаписываются при каждом вводе — нельзя выделить текст и скопировать вручную, не потеряв выделение.

### 1.4. Ошибки данных и открытых источников
- [ ] Нет слоя **открытых данных**: тарифы конкурентов, бенчмарки опозданий, стоимость ТМЦ.
- [ ] Нет **сопоставления Зисов с географией** (район, плотность, пробки) — а это ключ к тарифу.
- [ ] Нет **проверки на выбросы**: если пользователь ввёл `lateness = 30`, модель должна предупредить, а не молча посчитать.

## 4. Тестирование результатов через ИИ

### 4.1. Подготовка данных
- [ ] Сформировать **набор тест-кейсов** (минимум 10): разные комбинации метрик (хорошие, плохие, выбросы).
- [ ] Для каждого кейса — **эталонный отчёт** (ручной расчёт) в JSON.
- [ ] Сохранить **baseline** (неделя 1) и **target** (неделя 6) для каждого кейса.

### 4.2. Прогон через ИИ
- [ ] Отправлять в ИИ **только структурированный отчёт** (раздел 2.2), без лишнего текста.
- [ ] Требовать ответ **строго в JSON** по схеме:
  ```json
  {
    "strategy_name": "string",
    "actions": [{"action": "string", "impact_profit_rub_day": 0, "impact_metrics": {}, "risk": "low|mid|high", "confidence": 0.0}],
    "expected_profit_rub_day": 0,
    "expected_delta_vs_baseline_pct": 0,
    "data_sources_used": ["string"],
    "assumptions": ["string"],
    "open_questions": ["string"]
  }
  ```
- [ ] Валидировать JSON схемой (ajv или ручная проверка).
- [ ] Сравнивать **прогноз ИИ** с **фактическим расчётом модели** на неделе 6.

### 4.3. Метрики качества ответов ИИ
- [ ] **Точность прогноза прибыли**: MAPE между `expected_profit_rub_day` и расчётом модели.
- [ ] **Согласованность действий**: нет ли действий, противоречащих друг другу (например, «снизить тариф» и «поднять мотивацию» без бюджета).
- [ ] **Опора на открытые данные**: доля действий со ссылкой на источник.
- [ ] **Риск-скор**: сумма `risk` по действиям.
- [ ] **Воспроизводимость**: одинаковый отчёт + одинаковая температура → одинаковый JSON (или зафиксировать seed).

### 4.4. Поиск лучшей стратегии
- [ ] Прогнать **N прогонов** (минимум 5) на каждом тест-кейсе.
- [ ] Выбрать стратегию по критерию: **максимум прибыли при риске ≤ mid и точности ≥ 80%**.
- [ ] Сравнить стратегии ИИ с **простым правилом** (например, «сначала ТМЦ, потом опоздания») — ИИ должен быть не хуже.
- [ ] Зафиксировать **лучшую стратегию** в `strategy.md` с обоснованием и источниками.

## 8. Риски и как их снимать

| Риск | Как снимать |
|---|---|
| ИИ даёт красивый, но нереализуемый план | Блок «Ограничения реальности» + валидация действий по слотам/кураторам/бюджету |
| Веса потерь не откалиброваны | Прогон на открытых бенчмарках, сравнение с фактом, версия весов в отчёте |
| Открытые данные устарели или запрещены к использованию | Дата и лицензия в отчёте, ручная проверка, fallback на ручные бенчмарки |
| Разные прогоны ИИ дают разный результат | Фиксировать температуру/seed, минимум 5 прогонов, медиана |
| Отчёт разрастается и ИИ теряет фокус | Ограничить отчёт: цель, калибровка, таблица, топ-3 причин, ограничения, схема ответа |
